# 3. Сценарии использования

Для каждого сценария указаны участник, триггер, что делает harness и как выглядит «готово». Промпты лежат в
`harness/prompts/next-steps/` (`./help.sh prompt <n>`).

## UC-1 · Познакомить агента с незнакомым репозиторием

- **Участник:** разработчик + агент · **Промпт:** 01
- **Ход:** агент читает `AGENTS.md`, рубрику и список навыков; объясняет топологию по `docker-compose.yml`;
  запускает `make harness-list` и `make harness-fast`.
- **Роль harness:** только гайды (ничего не меняется). Отчёт показывает агенту, что здесь значит «зелёный».
- **Готово:** короткий и верный обзор: сервисы, граф вызовов, владение данными, события, сенсоры и какой навык
  подходит к какой задаче.

## UC-2 · Реализовать фичу «контракт сначала»

- **Участник:** агент · **Промпт:** 02 · **Навык:** `new-endpoint`
- **Ход:** написать контрактный тест → увидеть, что он падает → реализовать в сервисе-владельце за
  `require_caller()` → проксировать в gateway → цикл `make harness-fast` → `make harness-integration`.
- **Сенсоры:** ruff, semgrep (`sql-built-from-strings`, `unsigned-service-call`), contract, ревью (R2).
- **Готово:** контрактные тесты GREEN; в PR указано, какие тесты доказывают поведение.

## UC-3 · Безопасно изменить схему БД

- **Участник:** агент · **Промпт:** 03 · **Навык:** `db-migration`
- **Ход:** новый `V<n>__name.sql` с `GRANT` для роли-владельца; обратно совместимые колонки.
- **Сенсоры:** `migrations` — M1 именование, M2 уникальная версия, **M3 только дописывание** (правка
  закоммиченной миграции ловится относительно `MIGRATIONS_BASE`), M4 права выданы, M5 без пропусков;
  semgrep `ddl-outside-migrations`.
- **Готово:** `migrate` завершается с кодом 0 при `make up`; контрактные тесты GREEN.

## UC-4 · Добавить новый сервис

- **Участник:** агент · **Промпт:** 04 · **Навык:** `new-service`
- **Ход:** сначала добавить запись в compose и запустить `make harness-fast` *до написания кода*: сенсор
  топологии перечислит каждую недостающую часть с точным ключом compose, который нужно изменить.
- **Сенсоры:** topology T1 (вызывающий доверенный), T2 (ключ выдан и смонтирован), T4/T5 (порядок старта),
  T7 (правила алертов), T8 (переменная задокументирована), T9 (нет данных в репозитории); prom-rules в pipeline.
- **Готово:** топология чистая, у нового эндпоинта есть контрактные тесты, алерты существуют.

## UC-5 · Выйти из RED-отчёта

- **Участник:** агент (или Stop-хук / CI) · **Промпт:** 05 (`./help.sh prompt fix-red` встраивает отчёт)
- **Ход:** блокирующие сенсоры по порядку; минимальное исправление в причине; `make harness-one s=<id>`, пока
  не пройдёт.
- **Ограничения:** агенту нельзя править `harness.yaml`, сенсоры, фикстуры, рубрику или существующие
  контрактные тесты, чтобы стало зелёным; о слепых сенсорах сообщают, а не обходят их.
- **Готово:** отчёт GREEN на текущей ревизии (без пометок *stale*).

## UC-6 · Не дать агенту объявить «готово» раньше времени

- **Участник:** Stop-хук Claude Code (`harness/hooks/agent-stop.sh`)
- **Ход:** агент пытается завершиться с незакоммиченными изменениями → хук запускает `make harness-static` →
  RED → код выхода 2 → агент возвращается к работе с началом отчёта. Следующая попытка всегда разрешена
  (`stop_hook_active`), поэтому сломанный harness не зациклит агента.
- **Готово:** агент завершает работу только с зелёными статическими сенсорами или явно сообщает, почему нет.

## UC-7 · Ревью изменения перед коммитом / PR

- **Участник:** разработчик или агент · **Промпт:** 06
- **Ход:** применить `RUBRIC.md` правило за правилом (R1–R9) к незакоммиченному диффу; проверить покрытие
  контрактов/миграций/конфигурации; включить всё, что RED или BLIND.
- **Автоматический двойник:** сенсор `review-agent` применяет ту же рубрику через LLM в каждом быстром цикле
  (рекомендательно).
- **Готово:** «ready» или список блокирующих пунктов с file:line и исправлением.

## UC-8 · Выпустить изменение и держать CI зелёным

- **Участник:** разработчик / агент / CI · **Промпт:** 07
- **Ход:** `make harness-pipeline` локально (то же, что в CI) → прочитать `.harness/eval-report.md` → объяснить
  любое изменение метрик поиска → done-check → PR. CI запускает `./run.sh --full` и прикладывает отчёт.
- **Готово:** pipeline GREEN; eval в пределах `EVAL_TOLERANCE` от `eval/baseline.json` или изменение обосновано.

## UC-9 · Измерить качество поиска

- **Участник:** CI (pipeline) или разработчик (`make eval`)
- **Ход:** один раз на версию корпуса загрузить `eval/corpus.yaml` через публичный API → выполнить все запросы →
  recall@5 и MRR@10 (+ опционально LLM-судья judge@1 при `JUDGE_BASE_URL`) → сравнить с `eval/baseline.json`.
- **Готово:** ни одна метрика не ниже baseline − допуск; таблица по запросам в `.harness/eval-report.md`.

## UC-10 · Улучшать harness по данным (мейнтейнеры)

- **Участник:** мейнтейнер · **Промпт:** 08 · **Навык:** `harness-steer`
- **Ход:** `harness-stats` (что срабатывает часто / никогда / слепо) → `harness-coverage` (гайды FF-ONLY,
  сенсоры FB-ONLY, UNPROVEN) → предложить ≤ 3 изменений → реализовать с засеянным дефектом и тихой чистой
  фикстурой → `harness-test`, `harness-selftest`, `harness-coverage` → запись в CHANGELOG.
- **Готово:** новое правило срабатывает на своей фикстуре и молчит на чистом коде и на реальном репозитории.

## UC-11 · Внедрить harness в другой проект

- **Участник:** платформенная команда
- **Ход:** `python3 harness/install.py <project>` → копирует механизм и пишет манифест с подходящими сенсорами
  (topology при наличии compose-файла, migrations при наличии `db/migrations`, unit при наличии цели `make test`),
  не перезаписывая `AGENTS.md`, `CLAUDE.md` и конфигурацию ruff проекта →
  `make harness-coverage && make harness-selftest && make harness-fast` в проекте.
- **Готово:** GREEN с первого запуска (CI доказывает это на свежем проекте-образце: `make adoption-test`); coverage
  заявляет только те категории, которые проверяют установленные сенсоры.
- **Версионирование:** образ раннера закреплён (`HARNESS_IMAGE`); манифест и гайды принадлежат проекту;
  `template.version` фиксирует, с какой версией апстрима было последнее согласование.
