# 8. Планировщик: сотрудники, задачи, встречи и перепланирование с ИИ

Сервис `planner` планирует работу ИТ-специалистов банка. Он хранит сотрудников, их задачи в стиле Jira (название,
описание, критичность, статус, оценка, срок, зависимости) и встречи в стиле Outlook. Каждой задаче он ставит оценку
важности с объяснением и заполняет рабочую неделю каждого человека вокруг его встреч. По запросу языковая модель
меняет порядок задач человека по инструкции на обычном языке. Затем правила проверяют ответ модели: модель может
решить, что делать первым, но не может нарушить зависимость или переполнить день.

![План: загрузка команды и задачи](../assets/plan-team.png)

## Попробовать

```bash
./app.sh up --llm          # или ./app.sh up: без модели перепланирование вернёт план по правилам
./app.sh seed planner      # 11 сотрудников в 7 командах, 61 задача, 57 встреч; даты относительно сегодняшнего дня
open http://localhost:8081/#/plan
```

Ту же команду загружает и кнопка **Load the iBank IT team** на странице **Plan** портала. Повторная загрузка
переносит демо на текущую неделю и сбрасывает статусы задач: сотрудники, задачи и встречи обновляются по handle, key и id.

## Приоритет: почему задача важна

Каждая задача получает оценку, корзину и причины, которые портал показывает рядом с задачей.

| Признак | Баллы |
|---|---|
| критичность | blocker 100 · critical 60 · major 30 · minor 10 · trivial 3 |
| срок | просрочена +80 · сегодня +60 · через 1–2 дня +40 · через 3–5 дней +20 · через 6–10 дней +8 |
| кто её ждёт | +15 за каждую открытую задачу, зависящую от неё (не больше 3); ещё +10, если среди них есть blocker или critical |
| ход работы | в работе +10 · на ревью +5 |

Корзины: **do now** от 90, **next** от 50, **later** от 20, иначе **someday**. `blocked_by` перечисляет открытые
задачи, которых она ждёт, `blocks` — задачи, которые ждут её. Выполненные задачи сохраняют оценку, но идут последними.

## Расписание: неделя человека

- Рабочие дни — с понедельника по пятницу, 09:00–18:00, обед с 13:00 до 14:00. Время встреч — по часам офиса, без часового пояса.
- В день помещается не больше `capacity_hours` работы над задачами (часы фокуса; встречи идут сверху).
- Задачи идут в заданном порядке, по умолчанию в порядке правил (оценка, затем срок). Задача начинается, только когда
  её собственные открытые зависимости завершены в этом плане. Задачи режутся на куски не короче 30 минут, а оценки округляются до четверти часа.
- Зависимость от чужой задачи не задерживает задачу, но план о ней предупреждает (`waits for CORE-210 (todo, @aram)`).
- План предупреждает:
  - о задаче, которая закончится позже срока;
  - о днях, где встреч на 5 ч и больше;
  - о работе, которая не помещается в план;
  - о встречах в выходной день.

  Работа, которая не помещается, попадает в `unscheduled` с причиной.

## Перепланирование с ИИ

`POST /api/planner/plan/{handle}/ai {"instruction": "В пятницу меня не будет; сначала безопасность", "days": 5}`

1. Планировщик отправляет модели:
   - данные о человеке;
   - дни плана с часами встреч;
   - все открытые задачи с оценкой правил, критичностью, статусом, оценкой времени, сроком, зависимостями и описанием;
   - инструкцию.
2. Модель отвечает JSON: `order` (каждый ключ один раз), `notes` (почему задача на этом месте), `days_off` (даты
   плана, которые освобождает инструкция) и `summary`.
3. Ответ читается строго:
   - неизвестные ключи отбрасываются;
   - пропущенные дописываются в порядке правил;
   - выходные могут быть только днями плана.

   Затем тот же планировщик раскладывает неделю в порядке модели, так что зависимости, встречи и ёмкость соблюдаются.
4. `source` равен `model` (вместе с `model`, `notes`, `days_off` и `changed` — сколько позиций сдвинулось). Если
   пригодного ответа нет, `source` равен `rules`, а `fallback` объясняет почему: модель не настроена, недоступна или ответила не JSON.

Модель — тот же эндпоинт, что у чата (`CHAT_LLM_URL`, `CHAT_MODEL`, `CHAT_LLM_API_KEY`). Как и любой вызов модели в
системе, он идёт только через `common.llm.ChatModel`.

## Граф работы

`GET /api/planner/graph` возвращает:

- людей (`e:<handle>`);
- их самые важные открытые задачи (`t:<key>` с критичностью, статусом, оценкой и корзиной);
- рёбра `assigned` (человек → задача) и `depends_on` (задача → задача);
- рёбра `meets` между людьми с весом — числом общих встреч за ближайшие 5 рабочих дней.

С параметром `handle` граф содержит задачи человека, задачи, которых он ждёт, и задачи, которые ждут его. Портал
рисует его тем же силовым графом, что и граф знаний. Этот граф строится из Postgres по запросу и не хранится в Neo4j.

## API (gateway)

| Метод и путь | Что делает |
|---|---|
| `POST /api/planner/employees` | добавить или обновить сотрудника: `handle`, `name`, `role`, `team`, `capacity_hours` (0–10, по умолчанию 6) |
| `GET /api/planner/employees?team=&start=` | все (или команда) с загрузкой: `open_tasks`, `open_hours`, `overdue`, `urgent`, `meeting_hours` (ближайшие 5 рабочих дней), `load` (открытые часы ÷ 5 дней фокуса) |
| `POST /api/planner/tasks` | добавить или обновить задачу: `key` (`PAY-101`), `title`, `description`, `severity`, `status`, `assignee`, `estimate_hours`, `due`, `depends_on`; 422 для неизвестного исполнителя или зависимости от самой себя |
| `GET /api/planner/tasks?assignee=&severity=&status=&project=&q=&sort=&start=&limit=` | задачи с `score`, `bucket`, `reasons`, `blocked_by`, `blocks`. `status` — `open` или один статус; `severity` можно повторять; `sort` — `priority`, `due`, `severity`, `estimate` или `key` |
| `GET /api/planner/tasks/{key}` · `POST /api/planner/tasks/{key}/status` | одна задача; перевести её в `todo`, `in_progress`, `review` или `done` |
| `POST /api/planner/meetings` · `GET /api/planner/meetings?attendee=&start=&days=` | добавить или обновить встречу (`id`, `title`, `starts_at`, `ends_at`, `organizer`, `attendees`); список |
| `GET /api/planner/plan/{handle}?start=&days=` | план по правилам: `order`, `tasks`, `days` (встречи и запланированные куски), `unscheduled`, `warnings`, `finishes`, `summary` |
| `POST /api/planner/plan/{handle}/ai` | перепланирование моделью с проверкой правилами (выше) |
| `GET /api/planner/graph?handle=&team=&start=&limit=` | граф работы |

`start` (дата) заменяет «сегодня», и ответы становятся воспроизводимыми; контрактные тесты используют фиксированный понедельник.

|---|---|

| подключение | compose `planner` (доверяет `gateway`, свой ключ, `PLANNER_DB_PASSWORD`), маршруты gateway `/api/planner/*`, задание и алерты Prometheus |
